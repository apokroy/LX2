# Static build of libxml2 and libxslt for LX2

libxml2 and libxslt are compiled from the release sources — into COFF objects for Win64,
into an ELF archive for Linux64 — and linked into the Delphi executable through the
`LX2.Static` unit. `libxml2.dll` and `libxslt.dll` (`libxml2.so`, `libxslt.so`) are not
needed then; late binding through `LX2Lib.Load(FileName)` remains for builds that do
not put `LX2.Static` into a uses clause.

The objects are part of the repository: a consumer builds an application with plain Delphi
and never runs the C compiler. `Import.ps1` and `Build.ps1` are for updating the libraries.

```
Source\libxml2\   the library from a libxml2 release (Import.ps1), codegen\*.inc, Copyright, VERSION
Source\libxslt\   the libxslt\ directory from a libxslt release, Copyright, VERSION
Source\shim\      windows.h bcrypt.h winnls.h - the Win32 API, declared by hand
                  iconv.h lx2_iconv.c - iconv on top of MultiByteToWideChar
                  crt_shim.c - the printf family on top of __stdio_common_v* from ucrtbase
Gen\              headers generated by Build.ps1 from the release templates (not committed)
Lib\Win64\        the objects xml_*.o, xslt_*.o, shim_*.o (committed)
Lib\Linux64\      liblx2native.a - libxml2 and libxslt for x86_64-linux-gnu (committed)
Patches\          local patches to the imported sources, applied by Patches.ps1 (see below)
Pgo\train.c       training driver of the profile-guided build (Pgo.ps1)
Tests\            LX2StaticSmoke.dpr - run by Build.ps1 -Test
Import.ps1        updates the sources to stable releases, then applies the patches
Patches.ps1       applies (-Apply) or verifies (-Check) the patches with git apply
Build.ps1         checks the patches, builds the objects and the archive, checks the invariants, generates ..\Source\LX2.Static.pas
Pgo.ps1           profile-guided build: training run over a corpus, then Build.ps1 with another clang
```

The throughput benchmark lives in `..\Tests\LX2Bench` (`Bench.ps1`): parsing, serialization,
C14N, XPath and validation on a synthetic document or on a file, thread scaling, and a
`--verify` mode that prints hashes and diagnostics two builds of the objects must agree on.

## Updating and building

```
.\Import.ps1                                  # latest releases of the 2.15 and 1.1 series
.\Import.ps1 -LibXml2 2.15.4 -LibXslt 1.1.45
.\Build.ps1 -Test
```

`Import.ps1` takes the release archives by tag from the GNOME mirrors on GitHub; the module
list is read from the release's `CMakeLists.txt`, so changes in the file set (2.15 moved the
tables to `codegen\*.inc` and dropped `xmlunicode.c`) are picked up automatically. The
version series is pinned in the script, currently 2.15: upstream fixes only the newest minor
branch, and every new branch changes the API, so moving to the next one is a separate step
with a run of the LX2 tests. `Build.ps1` compiles with `bcc64x.exe` (clang 20 from the
`bin64` directory of RAD Studio, targets `x86_64-w64-windows-gnu` and `x86_64-linux-gnu`),
checks the invariants and generates `LX2.Static.pas`; the sources, `Lib\Win64`, `Lib\Linux64`
and the generated unit are committed. `-Platforms Win64` or `-Platforms Linux64` compiles one
side only; the unit is always generated for both from what `Lib\` holds. A plain Win64 build
replaces profile-guided objects, so after `Pgo.ps1` refresh the Linux side with
`-Platforms Linux64`.

## Profile-guided build

The parser loops are branchy and gain from a profile what no `-O` level gives: on real
documents about −10 % on a DOM parse, −30 % on a push parse, −20 % on C14N, −8 % on schema
validation. bcc64x builds instrumented code but rejects the profile on the way back
(`bad magic` for both the indexed and the text format), so `Pgo.ps1` uses another LLVM:
upstream LLVM 20, or the LLVM that ships with Visual Studio, whichever `-Llvm` names or is
found. It builds the training exe (`Pgo\train.c`, msvc target, Visual Studio C runtime),
runs it over the corpus — directories or files of `*.xml`, outside the repository, ideally
the documents the applications really process; a `<name>.xsd` next to a document adds
validation — merges the profile with `llvm-profdata`, then runs `Build.ps1 -Clang … -Profile …`:
the same target, flags and RAD Studio headers as the bcc64x build, so the objects link the
same way and, without a profile, run at the same speed. The objects and `LX2.Static.pas`
it leaves are committed like after a plain build; a later plain `Build.ps1` replaces them
with bcc64x objects again.

```
.\Pgo.ps1 -Corpus D:\Corpus\XML -Test
```

## Local patches

Changes to the imported sources live in `Patches\NNN-name.patch`, unified diffs with paths
relative to `Source` (`a/libxml2/parser.c`), each with a leading comment that says what it
changes, why, and whether it is upstream. `Patches.ps1` applies them with `git apply` on
the `Source` directory (no repository needed, line endings untouched): there is no fuzz, every
context line has to match, and a patch whose code has moved fails instead of landing
somewhere else.
`Import.ps1` applies the patches after copying a release, so a release that changed the
patched code stops the import until the patch is redone; `Build.ps1` checks before
compiling that every patch is applied, so a file reverted from SVN cannot produce objects
without the change. To make a patch: edit the file in `Source`, take the copy of the file
as it was before the edit (with every earlier patch applied), `git diff --no-index before
after`, rewrite the two path lines to `a/…` and `b/…`, add the comment on top and the
name to `Source\PATCHES`.

`Source\PATCHES` records the patches applied, in order; `-Check` compares it with
`Patches\` and then removes the patches in reverse order from a copy of `Source`, each
must come off cleanly. A later patch may build on an earlier one.

Current patches:

- `010-chardata-utf8-fast-path.patch` — `parser.c`: the fast loop of
  `xmlParseCharDataInternal` accepts complete UTF-8 sequences instead of handing every
  text node with a non-ASCII byte to `xmlParseCharDataComplex`.

Tried and dropped: a 16-byte SSE2 pre-scan of character data and of the text to
serialize. It pays only on long text nodes (a fifth off a SAX parse of 1.4 KB notes) and
costs 5–8 % of a SAX parse on documents with short text, which is what the bank formats
are; the parser's byte loops are cheaper than a block test per text node.

## How it links without a C runtime

The libraries need a C runtime: `mem*`/`str*`, `malloc`, stdio for files, `printf` in error
messages, `strtod` and the XPath math. The mingw runtime never enters a Delphi executable,
so:

- everything that `ucrtbase.dll` exports (present on every Windows 10 and later) is declared
  in `LX2.Static.pas` as `external 'ucrtbase.dll'`; Pascal never calls these names, the
  declarations exist for the linker only, and they carry no signatures;
- `snprintf`, `vsnprintf`, `fprintf`, `vfprintf`, `sscanf` are not exported by ucrtbase (in
  MSVC they are inline wrappers in the headers); `Source\shim\crt_shim.c` provides them on
  top of `__stdio_common_vsprintf` and its siblings, and likewise the POSIX names
  `open`/`close`/`read`/`write`/`dup` on top of the underscore forms;
- the Win32 API is declared by hand in `Source\shim\windows.h`, without `dllimport`,
  because bcc64x ships no SDK headers; the objects reference the functions by name and the
  Pascal side covers them with `external 'kernel32.dll'` and `'bcrypt.dll'`;
- the clang stack probe `___chkstk_ms` (frames larger than a page) is implemented in
  `LX2.Static.pas` in assembler;
- iconv is `Source\shim\lx2_iconv.c`: libxml2 always converts between UTF-8 and the document
  encoding. Single-byte code pages (windows-1251, KOI8-R, ISO-8859-x) convert through
  tables built at `iconv_open` from the Windows mapping of the 256 bytes, so the loop
  itself makes no API calls; everything else goes through UTF-16 and
  `MultiByteToWideChar`, UTF-16 and UTF-32 are handled directly. The POSIX iconv
  semantics (`E2BIG`, `EILSEQ`, `EINVAL`) that libxml2 relies on hold on every path.

After compilation `Build.ps1` compares the unresolved symbols of every object with the list
of names covered by `LX2.Static.pas`: a new dependency of a fresh release fails the script,
not the link on a colleague's machine. Global constructor sections are forbidden in the
objects, dcc does not run them.

## Linux64

dcclinux64 knows neither `{$L}` nor `{$LINKLIB}`, so the 51 objects go into one archive,
`Lib\Linux64\liblx2native.a`, and the Linux half of `LX2.Static.pas` declares every entry
point as `external 'liblx2native.a' name '…'`; the application puts `Lib\Linux64` on its
library path (`--libpath` of dcclinux64, the platform's Library path in the IDE). The
archive keeps libxml2 and libxslt together: the linker takes the members it needs. The
build needs a PAServer SDK (`-LinuxSdk`, or Default_Linux64 of the IDE); `-Test` links the
smoke test with dcclinux64 and runs it in WSL.

- No shims: `Source\shim` is a Windows matter. The C runtime, the math, pthreads and iconv
  are glibc, `config.h` for Linux is written to `Gen\Linux64`.
- The glibc names the objects may reference are a closed list in `Build.ps1`
  (`$GlibcImports`), all present in glibc 2.33. It is not a formality: with `_GNU_SOURCE`
  (or `-std=c2x`) the headers of glibc 2.38 redirect `sscanf` and `strtoul` to
  `__isoc23_sscanf` and `__isoc23_strtoul`, and the executable stops loading on every
  distribution with an older glibc. Hence `-std=gnu11` without `_GNU_SOURCE`.
- bcc64x does not define `__STDC__` for the Linux target in C mode and `sys/cdefs.h` of
  glibc stops the compilation; the script passes `-D__STDC__=1`.
- The floor of the archive is glibc 2.33; the oldest target is Ubuntu 22.04 with 2.35 (24.04
  has 2.39, 26.04 has 2.43, RED OS 8 has 2.36). The floor comes from `stat()`: since glibc
  2.33 it is a function `stat64`, before that an inline wrapper over `__xstat64`, and an
  object compiled against one generation of headers does not link against the libc of the
  other. Going lower (Ubuntu 20.04, glibc 2.31) would take a `stat` replacement on top of
  `statx`; it was tried, works, and was dropped together with that target. `getentropy` came
  with 2.25, everything else is older.
- The archive is only half of the matter: the symbol versions an executable asks for come
  from the SDK it is linked against, so an application is linked against the SDK of the
  oldest system it has to run on.
- The per-thread state of libxml2 lives under a pthread key (`pthread_getspecific`), not in
  ELF thread-local storage: the archive has no `.tbss`/`.tdata` and needs no TLS relocations.
- The profile-guided build is Win64 only.

## Features and flags

The libxml2 feature set is defined in `Build.ps1` (`$LibXml2Features`): no HTTP, modules,
zlib or lzma; documents come from memory and streams, and each of these features pulls in
its own library or a DLL load. RelaxNG, Schematron, XPointer, XInclude and the debug dumps
(`debugXML.c`) are off too: the binding declares none of their functions, and dcc links an
object whole, so whatever `xmlreader` or `xmlschemas` referenced went into every executable.
The entry points of the binding that these modules implemented stay `nil`
(`xmlTextReaderRelaxNG*`, `xmlSchemaDump`); `XML_PARSE_XINCLUDE` and
`xsltSetXIncludeDefault` are accepted and do nothing. `Import.ps1` does not copy the modules
of a feature that is off, so switching one back on starts with re-importing its module.
What stays and why: the HTML parser and serializer, because libxslt calls them without a
guard (`xsl:output method="html"`); xmlWriter, because `xmlTextReaderReadInnerXml` and
`ReadOuterXml` are built on it; pattern and regexps, which XML Schema needs; catalogs and
SAX1 (`xmlParseDoc`, `xmlParseFile`, `xmlParseMemory`), which the binding exposes.
libxslt without the debugger and trio, with the profiler.

```
--target=x86_64-w64-windows-gnu -std=c11 -O3 -fno-math-errno -DNDEBUG -DLIBXML_STATIC -DLIBXSLT_STATIC -DHAVE_CONFIG_H
```

Speed over size: `-O3` gives the parser loops full inlining and vectorisation,
`-fno-math-errno` lets clang treat the XPath math (`floor`, `fmod`, `pow`, `sqrt`) as pure
functions, libxml2 never reads `errno` after them. Frame pointers are omitted and there is
no stack protector, both are clang defaults for this target. The baseline ISA is x86-64 with
SSE2, no `-march`: the libraries do not dispatch on CPUID, and an object with AVX would crash
on CPUs without it. Link-time optimisation is not available: dcc links the objects one by
one and cannot consume bitcode.

## Using it from a program

```delphi
uses libxml2.API, libxslt.API, LX2.Static;
...
LX2Lib.Initialize;   // binds to the objects; LibraryFileName is empty
XSLTLib.Initialize;
```

`LX2.Static` assigns `LX2Lib.StaticBinder` and `XSLTLib.StaticBinder` in its
`initialization` section; with a binder assigned, `Load` does not load a library file. The
build covers Win64 and Linux64; Win32 and the other platforms are not built, the unit is
empty there and `Load` keeps loading the library file (`libxml2.dll`, `libxml2.so.16`).
